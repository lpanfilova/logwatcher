# LogWatcher + AI Project Documentation

## Overview

LogWatcher + AI is a FastAPI-based log monitoring service that ingests structured JSON logs, stores recent events in memory, raises simple alerts for suspicious patterns, and lets users ask natural-language questions about recent logs using OpenAI.

The application is built around four main concerns:

- **API layer** using FastAPI for health checks, alert retrieval, log viewing, export, and AI-assisted querying.
- **In-memory log storage** using a ring buffer for fast recent-log access and lightweight filtering.
- **Watcher/alerting logic** for repeated database failures and slow query spikes.
- **AI integration** that turns plain-English questions into structured filters and explains matched logs.

## Core Architecture

### 1. API Server

The FastAPI application in `app.py` creates global instances of:

- `LogStore` for recent log retention
- `Watcher` for alert generation
- an in-memory subscriber list for Server-Sent Events (SSE)

At startup, the app launches a background ingestion task. The current implementation is configured around a backend polling mode and explicitly rejects Docker log mode during runtime.

### 2. Log Storage

`LogStore` stores `LogEvent` objects in a `deque` with a fixed maximum length. This gives the project ring-buffer behavior:

- newest events are retained
- oldest events are discarded automatically when capacity is exceeded
- recent logs can be returned quickly
- recent logs can be filtered without needing a database

Supported query filters include:

- `since_minutes`
- `event`
- `level_min`
- `route_contains`
- `userId`
- `durationMs_min`
- `latencyMs_min`

### 3. Alerting

`Watcher` maintains rolling counters over a 60-second time window and emits alerts when thresholds are reached.

Current rules:

- `db_connection_failed` count >= 2 in 60 seconds → `DB_CONNECTION_FAILURE_SPIKE`
- `db_query_slow` count >= 3 in 60 seconds → `DB_SLOW_QUERY_SPIKE`

The watcher also applies cooldown-based deduplication, so the same alert type cannot fire again until the cooldown expires.

### 4. AI-Assisted Log Queries

`ai_client.py` provides two key functions:

- `build_filter_from_question(question)`
- `explain_results(question, filt, matched)`

The first uses an OpenAI chat completion call to convert a natural-language question into a structured filter object. The second summarizes matched logs while being instructed not to invent evidence outside the matched results.

If the AI output cannot be parsed as JSON, the code falls back to a safe default filter.

## Data Models

### `LogEvent`

Represents one structured JSON log line. Required fields:

- `level`
- `time`
- `service`
- `event`

Optional fields include request metadata, DB timing information, auth fields, and nested error details.

### `AskRequest`

Used by `POST /ask`.

- `question`: natural-language query
- `max_logs`: maximum recent logs to scan

### `AskResponse`

Returned by `POST /ask`.

- `filter_used`
- `matched_count`
- `answer`

### `Alert`

Represents an emitted watcher alert with a summary and a sample of recent interesting events.

## API Endpoints

### `GET /health`
Returns a service health snapshot including mode, storage counts, and subscriber count.

### `GET /alerts`
Returns the latest alerts generated by the watcher.

### `POST /ask`
Accepts a natural-language question, generates a filter, queries recent logs, and returns an AI-generated explanation based only on matched events.

Example request:

```json
{
  "question": "Show slow queries in the last 10 minutes",
  "max_logs": 200
}
```

### `GET /logs/recent`
Returns the most recent log events as JSON.

### `GET /logs/export`
Exports recent logs in either JSON or CSV format.

Supported query parameters:

- `format=json|csv`
- `limit=1..10000`

### `GET /logs/stream`
Streams logs live using Server-Sent Events.

### `GET /logs`
Serves a simple browser-based live log viewer that first loads recent logs and then subscribes to the live SSE stream.

## Log Ingestion Flow

The intended ingestion flow is:

1. raw JSON log arrives from a source
2. it is parsed into a `LogEvent`
3. `handle_event()` stores it in `LogStore`
4. `Watcher.ingest()` updates rolling counters and may emit alerts
5. the event is broadcast to connected live subscribers

`log_tail.py` still contains helpers for:

- tailing a normal file
- streaming `docker logs -f`
- rewriting a mirror file to cap retained line count

## Known Issues and Implementation Notes

1. **Missing imports in `app.py`**
   The current file uses `subprocess`, `io`, and `csv`, but those imports are not present in the shown code. This will cause runtime failures in container detection and CSV export unless corrected.

2. **Mode mismatch in `app.py`**
   The app still auto-detects a Docker container and raises an error if none is found, but startup later says Docker log mode is no longer supported in this deployment. That creates a configuration contradiction.

3. **Backend polling function reference**
   `startup()` calls `poll_backend_logs()`, but that function is not shown in the current visible section of `app.py`. If it is absent from the real file, startup will fail.

4. **API key file handling**
   Reading API keys from a plaintext file works for local demos, but environment variables or secret managers are safer for real deployments.

## Recommended Next Improvements

- add missing imports and validate all routes at startup
- resolve Docker/backend ingestion mode inconsistencies
- add endpoint tests using FastAPI's test client
- add structured logging for the LogWatcher service itself
- move secrets handling to environment-based or container-secret-based configuration
- add persistent storage if long-term log retention is needed
- add pagination or cursoring for large log exports
